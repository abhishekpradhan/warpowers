# Engine Notes — GeneralsX/ZH boot requirements (for the zero-retail dataset)

Condensed from a full source exploration + empirical bring-up, 2026-08-21. The Zero Hour build is the `GeneralsMD/` tree (`z_generals` target → `GeneralsXZH`); shared code in `Core/`; `GeneralsZH/` holds only GeneralsX's replacement `ExtrasMenu.wnd`.

## The three-bucket shape of the minimal dataset

1. **~46 must-exist INI paths** — the engine hard-dies (`throw INI_CANT_OPEN_FILE` → `RELEASE_CRASH`) on any missing one, but shrugs at dangling references inside them (all cross-reference validators are no-op in release). Each `Data\INI\X` demand is satisfied by `Data/INI/X.ini` *or* any `.ini` inside `Data/INI/X/`. Full list lives in our authored dataset (`data/Data/INI/**`).
2. **Exactly one must-exist binary asset:** ≥1 music file — `GameEngine.cpp:622` silently sets quitting if no `MusicTrack`'s resolved file exists on disk. Path = `AudioSettings.AudioRoot\MusicFolder\Filename`. (Ours: `wp_ambient_01.mp3`.)
3. **A handful of must-exist WND layouts** whose absence causes null-deref segfaults, not clean errors: `Menus/MainMenu.wnd`, `Menus/BlankWindow.wnd`, `ControlBar.wnd` (+ every named child the code references — we generate all 117), `GeneralsExpPoints.wnd`, `ControlBarPopupDescription.wnd`, `ReplayControl.wnd`. Missing WND *file* → `winCreateFromScript` returns null harmlessly; missing named *window* → crash at the unguarded lookups.

Everything visual degrades gracefully: missing W3D model → invisible object; missing texture → magenta placeholder; missing shader → logged error; missing CSF strings → raw labels.

## Key mechanics

- **Loose files beat archives; archives are optional.** `StdBIGFileSystem` mounts every `*.big` (no hardcoded names) but boots happily with zero. Ship everything loose.
- **Asset root resolution** (in order): `$CNC_GENERALS_ZH_PATH` → `$GENERALSX_ASSET_PATH` → `$CNC_ZH_INSTALLPATH` → `Options.ini [Paths]` → registry.ini → `<exedir>/../Resources` → `<exedir>` → CWD. run.sh cd's to the game dir, so CWD wins.
- **User data dir** (saves, maps, registry.ini): `~/Library/Application Support/GeneralsX/GeneralsZH/`. User maps ARE disk-scanned; asset-root `Maps/` needs `MapCache.ini` unless `-buildmapcache` (which we patched into release).
- **Singleton INI blocks** must exist or `OVERRIDE<T>` globals stay null and later deref: `WaterSet <TOD>` ×4 + `WaterTransparency` (Water.ini), `Weather` (Weather.ini). Same pattern likely for others as we go deeper.
- **`Object DefaultThingTemplate` is load-bearing** (ThingFactory.cpp:137): every new object template copies its baseline from a template literally named `DefaultThingTemplate`. The ThingTemplate ctor never initializes `m_assetScale`, so without this template every model is created at **scale 0** (vertices collapse to −0.0 — invisible, no error). Ours sets `Scale = 1.0`; retail's sets many more baselines — expect more zero-default finds seeded here.
- **`W3DDefaultDraw` is a no-op in release builds** (constructor body is `#ifdef LOAD_TEST_ASSETS`); INI-declared objects must use `W3DModelDraw` with `DefaultConditionState / Model = <name> / End`.
- **GameData zero-defaults found so far** that retail INI normally sets: `PartitionCellSize` (0 → shroud div-by-zero), `CameraPitch/CameraHeight` (0 → horizon-staring camera). `ShroudOn = No` is a valid data toggle.
- **W3D models**: `tools/genw3d.py` generates engine-valid meshes (byte spec from the GPL reader; see the tool). **RESOLVED 2026-08-22 — the "invisible mesh bug" was never a rendering bug.** Meshes rendered correctly all along; in every unattended run the mouse cursor sat at screen corner (0,0), the RTS **edge-scroll** marched the camera off the base within ~2s of match start, and the meshes were then *correctly* frustum-culled. They did render during the first frames — under the fade-from-black — which is exactly the window all budget-capped instrumentation sampled, manufacturing days of false "draws submit, no pixels" evidence. Fix for the headless dev loop: `HorizontalScrollSpeedFactor = 0.0` / `VerticalScrollSpeedFactor = 0.0` in GameData (restore for real input work). Two secondary data findings: `UseBehindBuildingMarker = No` (with it on, structures are routed to the stencil-occlusion flush path, unverified on this port), and maps must be big enough for the camera-area constraints at CameraHeight (a 640×640-world map collapses the constraint box; WPTest is now 160×160 cells = 1600×1600). **Lessons burned in:** (1) never trust budget-capped logging to characterize steady-state behavior — always run an unbudgeted long-horizon counter first; (2) before instrumenting a draw pipeline, verify the camera is looking at the object *in the failing frames*, not in frame 1. The GPU-forensics detour still paid: three real latent bugs found and fixed in the DXVK fork (see below), plus a validated Metal/Vulkan instrumentation toolkit (`WP_DXVK_SPY` in the fork; MoltenVK-source spies in `~/MoltenVK-src`, not shipped).
- **Transition groups:** every name in code must exist in `WindowTransitions.ini` (56 names, predefined) — engine bug: `remove()` on unknown name null-derefs via `null == null` (patched in our branch).
- **The `-file` direct-load path fights the shell, twice** (both fixed on our branch, 2026-08-22). (1) Nothing pops the shell: MainMenu's full-screen window stays visible-status over the running game and swallows every drawable pick in `W3DView::pickDrawable` (`getWindowUnderCursor`), so clicks select nothing — fixed by popping shell screens in `GameLogic::startNewGame`. (2) With the menus popped, `Intro::doPostIntro`'s **render freeze** (`m_breakTheMovie=TRUE`, meant to hold the screen until MainMenu fades in and normally cleared by `MainMenuInit`) is never cleared — `W3DDisplay::draw` then skips its entire scene-render block forever. The game still *runs* (logic, input, castRay all live) but no `Visibility_Check` ever executes, so every render object keeps its creation-default visibility bit: map-placed objects happen to be visible, production-spawned units stay `Is_Really_Visible()=0` — invisible AND unpickable (castRay gates on it). Cost days of shroud/ghost-object false trails; the tell that cracked it was instrumenting `Visibility_Check` and finding it never ran. Fix pair: clear the flag in `startNewGame`, and gate `doPostIntro` on `TheShell->top()` existing. Lesson: when a *state bit* is wrong, first verify the *writer of that bit runs at all* before theorizing about which write is wrong.
- **Fog of war works with 100% original data**: `ShroudOn = Yes` (retail default) runs the full partition shroud pipeline — enemy objects beyond vision are `OBJECTSHROUD_SHROUDED` and unrenderable/unpickable, own-vision circles clear via `VisionRange`/`ShroudClearingRange`, terrain shroud draws as black falloff. The ghost-object snapshot system (fogged-building memory) also engages cleanly.
- **Win/lose conditions in `-file` mode are map scripts** (VictoryConditions proper is multiplayer-gated). The `PlayerScriptsList` chunk must be **nested inside `SidesList`** (the map reader only registers it there — `SidesList::ParseSidesDataChunk`; the top-level registration is for `.scb` files only); `ScriptList` sub-chunk order maps 1:1 to side order. Chunk formats from the Scripts.cpp writers: Script v2 (name + 3 comment strings + 6 flag bytes + delayEvaluationSeconds int) containing OrCondition v1 (nested Condition v4 chunks) + ScriptAction v2 chunks. **v4/v2 condition/action chunks carry the internal-name key and the engine rematches the type by name** — write ordinal 0 plus the name (`NAMED_DESTROYED`, `VICTORY`, `LOCALDEFEAT`) and skip fragile enum counting; Parameter type ordinals ARE positional (`Parameter::UNIT` = 14; params serialize as int type + int + float + string, COORD3D excepted). Map objects get script names via the `objectName` dict key (→ `Object::setName` → the script engine's named-object cache; `NAMED_DESTROYED` also stays true after the object is fully removed, via `didUnitExist`). `VICTORY` = input off + 120-frame banner + `exitGame`; after a `-file` match the engine already quits to desktop (`m_initialFile` check in `GameLogic::clearGameData`). Two crash fixes on the way out (our branch): `Shell::doPush` null-derefs when the pushed layout file is missing (post-game `ScoreScreen.wnd`); `~DX8VertexBufferClass`/`~DX8IndexBufferClass` deref dead D3D buffers when subsystems (TerrainTracks via `~GameClient`) are destroyed after device shutdown — this was the "pre-existing SIGTERM shutdown crash", and it fires on every clean quit too.
- **Flags in release build:** `-win -fullscreen -headless -xres -yres -noshellmap -noShellAnim -nologo -quickstart -mod -noshaders`, plus our patch adds `-file <map>` (menu bypass) and `-buildmapcache`. `-map/-noaudio/-nomusic/-novideo` remain debug-only upstream. **`-headless` skips ALL GUI/WND/SDL/Vulkan — the future CI harness.**
- **Language:** resolves to `english` via the port's registry.ini default; `Data/english/` holds Language, HeaderTemplate, CommandMap.

## macOS build gotchas (hard-won)

- Build needs `VCPKG_ROOT` and the LunarG SDK env: `source ~/VulkanSDK/1.4.357.1/setup-env.sh` (the build script checks the SDK but doesn't export `VULKAN_SDK` — upstreamable fix).
- `RTS_DEBUG_CRASHING=ON` does not compile on macOS (MSVC `__int64` in Debug.h profile structs).
- **Never `cp` over a previously-executed binary** — same-inode replacement trips the kernel's signature cache → instant SIGKILL (exit 137, zero output). `rm` first (deploy script needs this fix).
- Piping build commands through `tail` masks their exit codes. Don't.
- Crash-report line attribution in RelWithDebInfo is unreliable (a "ThingFactory::reset" stack was actually a different site); `fprintf` breadcrumbs + rebuild beat forensics.
- **DYLD_INSERT_LIBRARIES is stripped when exec'ing SIP-protected binaries** (i.e. `/bin/bash`, so any env you set before `run.sh` is gone by the time the game launches). Compose the full env inline and exec `./GeneralsXZH` directly, the way our test harness does.
- **Never touch Metal (create a device/encoder) inside a dyld initializer** — the AGX driver's lazy internal-shader compile aborts the process (SIGABRT in `getRangeExecutionVariant`). Defer to a dispatch_after.
- **Present blocks forever when the window is occluded** (locked screen): CAMetalLayer starves drawables → DXVK `Presenter::acquireNextImage` waits on a condvar indefinitely. Use `WP_PRESENT_SKIP=100000000` (engine feature) for headless runs; `WP_FRAME_DUMP` still captures real frames. Also: a game stuck there survives `pkill` (TERM) — a zombie instance then poisons later runs; use `pkill -9` and check `pgrep` before every run.
- The engine's own shutdown crashes in `TerrainTracksRenderObjClassSystem::shutdown()` on SIGTERM (pre-existing destructor bug, harmless noise in crash reports).
- ObjC-swizzle spies cannot see MoltenVK's encoder calls usefully (dispatch goes through per-frame recreated encoders + selector stubs; our hooks verified installed yet never fired for reasons ultimately mooted by the real root cause). The productive instrumentation layers are: DXVK source (we own it), MoltenVK source (built from `~/MoltenVK-src`, `make macos` with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`), and engine breadcrumbs.

## DXVK fork fixes found during the hunt (all committed on `warpowers-dxvk`)

1. **Dummy vertex binding bound with length 0** → every null-attribute fetch was out-of-bounds, undefined without robustness2 (the exact configuration the fallback exists for). Now binds the dummy's full length.
2. **Dummy vertex binding stride 0** → with dynamic strides, Metal gets `attributeStride:0` on a per-vertex layout and the AGX driver silently kills the draw. Visible symptom: far-terrain rows missing (their fix restored them). Now stride 16.
3. **Spec-constant UBO never created without `VK_EXT_graphics_pipeline_library`** (which MoltenVK lacks; our patchset waives DXVK's requirement) → every shader's `spec_state` pointer in the Metal argument buffer was NULL, a latent GPU null-deref for any pipeline variant that reads it. Now always created/bound on `__APPLE__`.

- **The build-button UI works with generated windows** (2026-08-22 late). The old "ControlBar window-lifecycle mystery" dissolved on measurement: the ControlBar layout is created once in `InGameUI::init` → `createControlBar()` and never destroyed — the failing `MoneyDisplay`/`PowerWindow` lookups failed because our hand-authored ControlBar.wnd simply never contained those windows, and the old money/power debug bail then silently returned out of `InGameUI::update` *before* `TheControlBar->update()`, so the whole context-sensitive command UI never ran in any match. `tools/genwnd.py` now generates ControlBar.wnd (48 windows): `ButtonCommand01..18` (`MAX_COMMANDS_PER_SET`) under `CommandWindow`, `ButtonQueue01..09` (`MAX_BUILD_QUEUE_BUTTONS` — **deref'd unguarded** in `populateBuildQueue`, hard requirement) under `ProductionQueueWindow`, `MoneyDisplay` (STATICTEXT) + `PowerWindow`. Click wiring: a gadget's GBM_SELECTED goes to its *owner* (itself by default), so buttons and their containers need `SYSTEMCALLBACK = "PassSelectedButtonsToParentSystem"` to bubble the message up to `ControlBarParent`, whose `"ControlBarSystem"` callback routes unrecognized button ids to `ControlBar::processContextSensitiveButtonClick` → the CommandButton's game message (UNIT_BUILD → `MSG_QUEUE_UNIT_CREATE`). Data side was already correct (CommandSet/CommandButton INI + `CommandSet =` on the object; `CANMAKE_OK == 0` — a logged `canMake=0` is success, not failure). Verified self-driving (`WP_CLICKTEST=ui`): click CC → selectCount=1 → ButtonCommand01 visible+enabled → click it → prodQ=1 → tank spawns. Also: `WP_FRAME_DUMP` TGAs are **top-down** (descriptor bit 0x20) — decode accordingly, or text looks mirrored and the UI looks upside-down (cost an hour chasing a nonexistent y-flip bug; `tgadiff.py` was always right).

- **Hidden tabs suspend the game entirely** (browser suspends `requestAnimationFrame` → the emscripten main loop never ticks → logic frozen, fade-from-black stuck, HUD fps garbage). Correct product behavior (auto-pause), but it perfectly impersonates an engine freeze during agent/pane-driven testing — check pane visibility before diagnosing "frozen logic" in the browser. In-browser interactive verification requires the pane visible; logic correctness stays covered by the native `WP_CLICKTEST`/`WP_AUTOTEST` harness.
- **Product shell (2026-08-22 night):** `web/index.html` is now a designed page — wordmark loading screen with byte-accurate progress (manifest carries file sizes; wasm fetched via `Module.instantiateWasm` with streaming byte counts), phase captions, error states with reload, letterboxed responsive canvas, hover fullscreen control, inline SVG favicon. Debug chrome is opt-in via `?debug=1` (log panel, `IG_TRACE=1`, in-game HUD via Options.ini `RenderFpsFontSize/SystemTimeFontSize/GameTimeFontSize` — 0 hides, engine default is 8/on). Console spam fixed: missing-label logged once (GameText), LSFS + d8web atlas probes behind IG_TRACE (d8web patched in the local dvijoke checkout — fork dvijoke at publish for provenance, add to D012 list).

## Stage 2 web build — FIRST BROWSER MATCH (2026-08-22 night)

**The Boot Slice match runs in a browser tab: 12MB of loose original data, no .big archives, full loop verified — CC select → build button → tank ($600 deducts) → move order pathfinds.** Engine branch `warpowers-web` = `warpowers` + merged `meerzulee/GeneralsXWeb` branch `igroteka-wasm` (GPL, same GeneralsX lineage; shared ancestor was already in our history so the ~3000-line patchset merged with six small conflicts). Renderer is **d8web** (github.com/meerzulee/dvijoke, MIT): D3D8→WebGL2, statically linked, expects a sibling checkout at `engine/../dvijoke`. Build: `emcmake cmake --preset wasm && cmake --build build/wasm --target GeneralsXZH.js` (emsdk latest; plain `cmake --preset wasm` silently uses the HOST compiler — always `emcmake`, and a stale host-configured build dir must be deleted). Post-merge fixes our newer base needed: emscripten window path in SDL3Main (no `SDL_WINDOW_VULKAN`), `__EMSCRIPTEN__` exclusion on the glibc `__forced_unwind` catch guards upstream added to the GameSpy threads, `RTS_BUILD_OPTION_DEEP_CRC=OFF` in the wasm preset. Web-side truths: loose-file asset root = process cwd → `FS.chdir('/game')` in the boot page (the `[ASSET_ROOT]` resolver only accepts `.big`-bearing dirs and its fallthrough leaves cwd at `/`); **MEMFS is case-sensitive where macOS wasn't** — first casualty was lowercase `data/Generals.str`, fixed with `FS.symlink('/game/Data','/game/data')`; expect more case bugs as data grows. Serving: `tools/genwebstage.py` → `webstage/` (engine js+wasm, gamedata + manifest, Liberation Sans for the wasm fontconfig stub) + any static server. Pending: native re-verification of the merged branch (their INI/mouse/SubsystemInterface changes also touch native paths), performance measurement, audio (their README lists it missing; MiniAudio partial), win-condition browser run, workspace submodule strategy once `warpowers-web` stabilizes.

- **`TerrainLOD = AUTOMATIC` (default) breaks shadows and particles on this port** (2026-08-22, beauty target). The first `W3DDisplay::draw` runs `calculateTerrainLOD()` — a 20-sample render benchmark that sets `drawTerrainOnly(true)` and on this port exits without restoring it, so `RTS3DScene::Customized_Render` early-returns before its tail forever: `queueShadows`/`queueParticleRender` never arm (`isShadowScene=0` every frame) while objects still draw through another path. Our GameData pins `TerrainLOD = MAX`. Decal shadows then just work: `UseShadowDecals = Yes` (GameData), `Shadow = SHADOW_DECAL` + `ShadowSizeX/Y` per template, default texture `shadow.tga` (multiplicative: white=no-op — make the visible fringe LARGER than the model footprint or it hides underneath; that cost an hour). Sizes ~2× footprint read right; small `ShadowOffsetX/Y` sells the sun angle.
- **VFX pipeline works end-to-end with authored data** (2026-08-22): ParticleSystem.ini (keyframe syntax `Color1 = R:x G:y B:z frame`, `Alpha1 = lo hi frame`; enum lists in ParticleSys.h), FXList.ini nuggets (`ParticleSystem/ViewShake/TerrainScorch...`), Weapon `FireFX`.
